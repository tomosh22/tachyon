### 3.9 Timeline level-of-detail (`libs/analysis/lod.h`, namespace `tachyon::analysis`)
For each thread, precompute at load: (a) state bands at levels L0..Lk where level L buckets have width `2^L × 64 ticks`, storing per bucket the fraction of Running/Ready/Waiting and the dominant wait category; (b) sample "mipmaps": for each level and bucket, the most frequent callstack id and its share, so the collapsed row can draw a representative color; (c) for expanded flame charts, per-depth run-length encoded spans built from consecutive samples sharing the same callstack prefix, merged when narrower than one pixel at the current zoom. Target: render any zoom level of a 10-minute, 64-thread capture in under 4 ms of CPU per frame.

Entry points: `TimelineLod::prepare()` (cheap: level geometry and the node table), `build()` (fills the per-thread data on `options.threads` workers; queries for threads that are not ready yet are answered by the exact direct path and may run concurrently with `build()`), and the convenience `buildLod(model, LodOptions, cancel, progress)`; not `lod::build(TraceModel&)`. Build progress fires per finished thread. Queries (thread-safe): `stateBands`, `sampleStrip`, `timeline` (the flame chart), and `rowColumns` (band + strip in one walk), each with `QueryMode::Auto` (LOD when the zoom allows) or `Direct` (always from `statesByThread` and the samples, the exact reference path). Accessors: `levels()`, `threadReady()`, `progress()`, `memoryBytes()`, `trimState()`, `degradedBaseLevels()`, `contentHash()` (determinism checks).

## Options and memory (`LodOptions`)
- Defaults: `threads` 0 (hardware concurrency; the result does not depend on it), `maxBaseBuckets` 2^20 per thread, `minSamplesPerBaseBucket` 4, `levelStep` **1** (one stored level per octave, so a pixel column holds at most 2 bucket starts; it was 2 before WP-64), `maxStacksPerBucket` 32 (exact below this), `fineStrip` true, `maxBytes` 0 (none), `forceBaseLevel` −1 (test hook).
- **Fine strip level:** with `fineStrip` (off when `forceBaseLevel` is set, the base level is L0, or the model has 2^24 or more callstack nodes) the build also stores, per half-base bucket (level L_base − 1), the packed sample-strip data (24-bit dominant leaf, 4-bit share, 4-bit coverage). In Auto mode `sampleStrip` answers pixel spans in [base/2, base) from it. Those answers are LOD approximations like every stored level; Direct mode and pixel spans below base/2 stay exact. Band and flame queries do not use it. A thread whose LOD is not built yet is answered by the exact direct path.
- **One-walk row query:** `TimelineLod::rowColumns(RowQuery, StateBandResult&, SampleStripResult&)` answers band and strip of one row in one column walk. Results equal separate `stateBands` + `sampleStrip` calls (same level, stack, category; weights within float rounding). Windows sticking out of the trace on either side, or lying entirely outside it, are valid and give empty columns there.
- **Memory:** about 6.26 B/sample on `large` with `levelStep` 1 and the fine level (1788 MiB; it was 4.59 B/sample with `levelStep` 2, 3.3 B/sample without the fine level). `LodOptions::maxBytes` (0 = none) makes `prepare` pick a coarser base level up front; then the fine strip level is not built and that zoom range is answered directly. `trimMemory(bytes)` frees the fine level, then the finest stored levels (always keeping the coarsest), only after the build finished; dropped zooms are answered directly from the samples (exact, slower). `trimMemory` is not thread-safe against queries (the viewer calls it on the main thread between frames). `trimState()` (a `LodTrim`: dropped levels, fine level dropped) and `degradedBaseLevels()` report what was dropped.

## Frame target status
The 4 ms target (64-row band + strip at 1920 px on `large`) is **not met** and is recorded as an exception: after WP-64 it measures 4.8 ms at the worst (direct-strip) zoom and about 4.2 ms at LOD-served zooms, +flame on 4 rows 4.8 ms, on the 4-vCPU dev VM; the test asserts 8 ms (2× the target, thread CPU time, best of 5 per zoom, worst zoom). The viewer queries 960 columns, about half the cost. The `medium` fixture meets the target (0.8 ms on CI). Per-query cost: a single row at any zoom (band + strip + 32-depth flame) is about 0.4 ms worst; LOD build on `large` takes 2.7–3.8 s with 4 workers (12.4 s with one).
